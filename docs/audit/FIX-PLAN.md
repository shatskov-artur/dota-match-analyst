## Живой симптом, с которого всё началось

Владелец открывает страницу The International, чтобы посмотреть расписание на завтра. В приложении
записан **один** матч (Falcons vs BB на 4 утра). На Liquipedia в это же время опубликованы **все
пять** матчей дня. Ничего не подтянулось автоматически, и владельцу пришлось идти спрашивать —
ровно то, чего проект существует чтобы не было.

## Диагноз (проверен по коду — цитируй эти места в коммитах)

**Первопричина 1 — расписание синкается только пока лига «в эфире».**
[server/src/services/ingest/ingestJob.ts:123](server/src/services/ingest/ingestJob.ts#L123):

```ts
const synced = await syncLeagues([...trackedLeagueIds, ...liveLeagues])
```

Набор лиг для 5-минутного синка сетки/расписания = явный список `TRACKED_LEAGUE_IDS` + лиги,
у которых **прямо сейчас** есть матч в `GetLiveLeagueGames`. После перехода на тир-политику
(аудит, находка E-1) явный список по умолчанию пуст. Следствие: между игровыми днями TI не
синкается **вообще**. Valve публикует расписание следующего дня поздно (после решения посевов) —
а спросить её некому, пока не начнётся следующий живой матч TI. Расписание замерзает на том,
что было опубликовано во время последнего live-матча. Это в точности симптом владельца.

Тот же изъян у discovery: [ingestJob.ts:134](server/src/services/ingest/ingestJob.ts#L134) —
ночное до-подтягивание ходит только по live-лигам, прошедшим тир-фильтр.

**Первопричина 2 — «интересные» лиги ниоткуда не берутся, кроме эфира.**
Проект уже знает про TI: строка лежит в таблице `leagues` (записана, пока TI был live), у неё есть
`end_timestamp` в будущем. Но никто не читает таблицу `leagues` как источник «за кем следить».
Единственный источник — сиюминутный эфир.

**Сопутствующее — тир турнира негде показать.**
`leagues.tier` ([db/schema.ts:38](server/src/db/schema.ts#L38)) хранит **валвовский integer**.
⚠️ **Шкала в этой строке была выдумана мной и неверна** — я написал «1=amateur, 2=professional,
3=premium», не проверив. По живому архиву (60 лиг): The International = **5**, все 59
общественных лиг = **1**; середина шкалы в данных не встречается вовсе и остаётся неизвестной. OpenDota-строка (`premium`/`professional`/
`amateur`), по которой работает `archivePolicy`, никуда не сохраняется — `getLeagueInfo` получает
её и использует только в моменте. UI не может показать тир, потому что BFF его не отдаёт.

# ЗАДАЧА A — расписание активных турниров синкается всегда, а не только в эфире

**Цель-приёмка:** расписание TI (и любого активного premium/professional турнира) обновляется
каждые ~5 минут независимо от того, идёт ли сейчас матч. Сценарий владельца: Valve публикует
5 матчей следующего дня в 23:00, когда эфир пуст, — к 23:05 они на странице турнира и в календаре.

## A1. Источник «лиги под наблюдением» — из архива

Новый модуль `server/src/services/ingest/leaguesOfInterest.ts` (или функция в `tournamentSync.ts` —
реши по месту, но НЕ в `ingestJob`, у него уже много ролей):

```
активные лиги = SELECT league_id FROM leagues
  WHERE end_timestamp IS NULL OR end_timestamp > now() - 3 дня
     -- и лига проходит архивную политику (shouldArchiveLeague — там уже есть мемо-кэш)
```

- Порог «+3 дня после конца» — чтобы турнир не пропал из синка в утро после финала (гранд-финал
  часто уезжает за полночь, а `end_timestamp` у Valve приблизительный).
- Фильтр через **существующий** `services/ingest/archivePolicy.shouldArchiveLeague` — не пиши
  второй экземпляр правила (это K3 из AUDIT-REPORT, за ним следят).
- Лиги, у которых `end_timestamp` нет вовсе, включай (Valve иногда не проставляет), но они
  отсеются политикой, если любительские.

## A2. Включить их в оба потока

В [ingestJob.ts:116-137](server/src/services/ingest/ingestJob.ts#L116-L137):

```ts
const ofInterest = await getLeaguesOfInterest()          // из БД, A1
const synced = await syncLeagues([...trackedLeagueIds, ...liveLeagues, ...ofInterest])
...
const found = await discoverTrackedMatches([
  ...await filterArchivableLeagues(liveLeagues), ...ofInterest,
])
```

- `syncLeagues` уже дедуплицирует и уже сортирует tracked-первыми
  ([tournamentSync.ts:458-465](server/src/services/ingest/tournamentSync.ts#L458)). Проверь, что
  cap `MAX_LEAGUES_PER_SYNC = 24` не выталкивает активные турниры в хвост: приоритет должен быть
  tracked → ofInterest → просто-live. Если сортировка сейчас двухуровневая — сделай трёхуровневую.
- Каждая лига = один keyless-вызов `GetLeagueData`, закэшированный на 5 минут (`TTL.LEAGUE_DATA`) —
  добавка из 1-3 активных турниров ничего не стоит.

## A3. Крайний случай: турнир анонсирован, но ни разу не был в эфире

Строки в `leagues` нет → A1 его не видит → до первого live-матча расписание не появится.
Закрыть дешёвым способом: **если** `TRACKED_LEAGUE_IDS` указан — он и так синкается (владельцу
достаточно один раз добавить id из `npm run find:league`). Автоматический вариант (опционально,
если останется время): раз в сутки пройтись по OpenDota `/leagues`, отфильтровать по
`tier ∈ {premium, professional}` и для кандидатов, которых нет в таблице `leagues`, дёрнуть
`GetLeagueData`; у кого есть будущие `scheduled_time` в нодах — засеять строку. Это отдельный
коммит; если реализуешь — с жёстким капом (не более ~20 проб GetLeagueData за проход) и логом.
Если не реализуешь — напиши в отчёте, что случай закрыт только ручным TRACKED_LEAGUE_IDS.

## A4. Тесты (обязательные)

- `leaguesOfInterest`: активная premium-лига попадает; закончившаяся 5 дней назад — нет;
  закончившаяся вчера — да (порог 3 дня); amateur — нет; ошибка политики → лига пропускается,
  не роняя список.
- Регрессия на симптом: юнит-тест на состав набора для `syncLeagues` — «TI в БД, эфир пуст,
  TRACKED пуст → TI в наборе». Это тот самый тест, которого не хватало.

## ✅ СДЕЛАНО — задача A (2026-08-15)

**A1.** Новый `services/ingest/leaguesOfInterest.ts`. Активные турниры читаются из таблицы
`leagues` (`end_timestamp IS NULL OR > now − 3 дня`), сортировка по дате конца (`nulls last`),
фильтр через существующий `archivePolicy.shouldArchiveLeague`, кап `MAX_LEAGUES_OF_INTEREST = 12`.
Лига без даты конца **включается** (Valve часто не проставляет), а от «каждого ладдера навсегда»
защищает тир-политика. Недоступный архив или упавший запрос → пустой список, не исключение.

**A2.** `syncLeagues` получил второй аргумент `ofInterest` и **трёхуровневый** приоритет
(`syncRank`: tracked → активные → просто-live) — с двумя уровнями вечер любительских игр мог
вытолкнуть TI за кап именно в тот день, когда публикуются его следующие матчи. Оба потока в
`ingestJob` теперь идут по трём источникам: синк расписаний и discovery.

**A3.** Реализован полностью, а не отложен. `getAllLeagues()` в `openDotaApi` (keyless каталог
всех лиг с тиром, кэш 6ч) + `services/ingest/seedAnnouncedLeagues.ts`: раз в сутки
(`SEED_ANNOUNCED_EVERY = 2880` тиков) берёт каталог, оставляет нужные тиры, отбрасывает уже
известные архиву, и пробует **не более 15** самых новых id (id растут монотонно — свежие
регистрации сверху). Строка заводится, только если в сетке есть фикстура в будущем в пределах
45 дней: Valve вечно хранит заброшенные шаблоны сеток, и «новый id» сам по себе не повод.

**A4.** Два новых файла, 25 тестов:
- `leaguesOfInterest.test.ts` (9) — включая именованный кейс «follows a running tournament on a
  day it is NOT playing», это регрессия ровно на симптом владельца.
- `syncPriority.test.ts` (6) — «TI между матчами + 30 живых ладдеров → TI всё равно опрошен и
  набор не превысил кап».
- `seedAnnouncedLeagues.test.ts` (10) — границы: заброшенный шаблон не заводится, amateur не
  опрашивается вовсе, бюджет проб соблюдён, каталог недоступен → тик не падает.

**Правка по ходу:** первый вариант `leaguesOfInterest` использовал `Promise.all`, и я написал
тест под это поведение — то есть закодировал баг. Исправлено на `allSettled`: одна лига с
недостижимым вердиктом стоит эту лигу, а не весь синк (иначе отказ политики глушил бы расписание —
ровно та поломка, которую модуль и закрывает).

**Верификация:** server tsc чисто, 30 файлов / 387 тестов зелёные (было 27/362).
**Не проверено:** живой прогон с ключами и Postgres — окружения нет. Задача A подтверждена юнитами.

# ЗАДАЧА B — тир турнира: сохранить и отдать наружу

**Цель-приёмка:** каждый турнир в API несёт человекочитаемый тир; клиент может фильтровать.

## B1. Хранить OpenDota-тир в `leagues`

- Новая колонка `od_tier: text` в таблице `leagues` ([db/schema.ts:35-49](server/src/db/schema.ts#L35)) +
  **миграция** (`npm run db:generate`, коммить сгенерированный SQL). Валвовский integer `tier`
  не трогать — они про разное.
- Заполнять в `syncLeague` ([tournamentSync.ts:94-145](server/src/services/ingest/tournamentSync.ts#L94)):
  тир уже фактически известен — `archivePolicy` спрашивал `getLeagueInfo` для решения о записи.
  Не делай второй запрос: либо прокинь тир из политики, либо дёрни `getLeagueInfo` — он
  закэширован 6ч, это бесплатно. В upsert: `odTier: coalesce(excluded, existing)` — транзиентный
  null не должен затирать известное значение (см. контракт B-1 в AUDIT-REPORT).

## B2. Отдать в API

- `/api/tournaments` уже возвращает строки `leagues` целиком — колонка приедет сама; добавь
  `odTier` в клиентский тип `Tournament` (`client/src/hooks/useArchive.ts`).
- `/api/live/games`: в `enrichLiveGames` ([liveAggregator.ts:47-56](server/src/services/liveAggregator.ts#L47))
  уже зовётся `getLeagueName(id)` на каждую лигу. Замени на `getLeagueInfo(id)` (тот же кэш,
  тот же вызов) и добавь в обогащённый матч поле `league_tier: string | null`. Обнови
  `EnrichedLiveGameSchema` в `schemas/bff.ts` и тип `EnrichedGame` на клиенте.

## B3. UI: фильтр по тиру над главной панелью

Владелец: «в фильтре над главной панелью добавь тир турниров, чтобы понимать, какой выбирать».

- Место: `client/src/components/MatchRail.tsx` — там уже живут чипы статусов и список лиг.
- Добавить ряд чипов **Tier 1 / Tier 2–3 / Other** (маппинг: `premium` → Tier 1,
  `professional` → Tier 2–3, всё остальное включая null → Other). Мультивыбор не нужен —
  одиночный, как статусные чипы; «все» по умолчанию.
- Состояние — в URL-параметр (`?tier=premium`), через существующий `patchParams` в
  `HomePage.tsx` — там уже есть образец для `show`/`league`.
- Фильтрация — в `client/src/utils/matchFilters.ts` (`applyFilters` — по `league_tier` матча;
  `applyEntryFilters` — для архивных записей потребуется тир в `/api/schedule/range`: добавь
  `leagues.odTier` в его select join, поле уже джойнится — [archive.ts:211-227](server/src/routes/archive.ts#L211)).
- В списке лиг фильтра — маленький бейдж тира рядом с названием (токены из `index.css`,
  никаких новых hex — см. H-2 в AUDIT-REPORT).
- Тесты: `matchFilters.test.ts` — фильтр по тиру, null-тир попадает только в Other/все.

## ✅ СДЕЛАНО — задача B (2026-08-15)

**B1.** Колонка `leagues.od_tier` (`text`) + миграция `drizzle/0001_windy_yellow_claw.sql`
(одна строка `ALTER TABLE`). Валвовский числовой `tier` не тронут — шкалы разные и одна из
другой не выводится. Заполняется в `syncLeague` без второго запроса: `getLeagueInfo` — тот же
6-часовой кэш, который политика архивации уже прогрела. В upsert — `coalesce(excluded, existing)`,
в отличие от соседних полей: недоступность OpenDota на один тик не должна стирать известный тир,
иначе турнир провалился бы в «Other» до следующего успешного запроса.

**B2.** `getLeagueName` в агрегаторе заменён на `getLeagueInfo` — **тот же самый вызов**, тир
просто перестал выбрасываться. В live-ответе появилось `league_tier`, схема `EnrichedLiveGameSchema`
обновлена (nullable, а не с дефолтом: «не знаем» и «amateur» — разные утверждения).
В `/api/schedule/range` добавлен `leagues.odTier` в оба select (ноды и серии), поле `leagueTier`
уходит в записи расписания — иначе фильтр не работал бы на прошедших и будущих днях.

**B3.** Ряд чипов **Any tier / Tier 1 / Tier 2–3 / Other** в `MatchRail`, сразу под статусами —
оба отвечают на «что тут вообще стоит открывать». Состояние в URL (`?tier=`) через существующий
`patchParams`. Фильтрация в `applyFilters` и `applyEntryFilters`. В списке турниров — бейдж
`T1`/`T2` токенами (`text-accent`/`border-border`, новых hex нет); «Other» намеренно **без**
бейджа: метка на двух третях обычного вечера не сообщает ничего.

**Тесты:** +10 в `matchFilters.test.ts` (32 всего) — маппинг тиров, регистр и пробелы от OpenDota,
`null` → Other, комбинация с другими фильтрами, и тот же фильтр на архивном дне. Фикстуры
`leagueOptions`/`leagueOptionsFromEntries` обновлены под расширенную форму `LeagueOption`.

# ЗАДАЧА D — повторный проход: ошибки и оптимизации

После A-C — короткий ревизионный проход своим взглядом. Правила из AUDIT-PROMPT.md действуют
(доказательность: файл:строка + сценарий; уровни; не выдавать стиль за дефект). Не переписывай
существующий AUDIT-REPORT — добавь в него раздел «Раунд 2 (дата)». Стартовые кандидаты, найденные
при подготовке плана (проверь и реши):

1. **Снапшот тащит в себе растущую историю.** `match_snapshots.payload` хранит обогащённый матч
   целиком, включая массив `history` (Redis-ряд до 240 точек) — к концу матча каждый снапшот
   несёт ~10KB дублируемого хвоста. Вариант: вырезать `history` из payload перед записью
   (страница при скрабе берёт ряд из `match_timeline`, см. `useMatchState.history` — проверь,
   что фолбэк на payload-history не единственный источник для каких-то случаев).
2. **Бандл клиента > 500KB** (warning при сборке). Кандидат: `React.lazy` на страницы
   Tournament/Series/Prematch + вынести героев/предметы-маппинги.
3. **`/api/schedule/range` дважды ходит в `tallySeriesWins`** (nodes + series) — можно одним
   запросом по объединённому набору seriesIds.
4. **`useMatchDetail` и MatchPage делят ключ `['live-games']` с разными интервалами** — работает,
   но хрупко; посмотри, можно ли свести к одному владельцу интервала.
5. `logger.debug` в archivePolicy на каждый отказ — в проде уровень info, не сработает; ок, но
   отказы по тиру стоит раз в тик агрегировать в один info-лог (`skipped: {amateur: 12}`), иначе
   владелец не видит, ЧТО именно не пишется.

## ✅ СДЕЛАНО — задача D (2026-08-15)

Из пяти кандидатов сделаны три, один отклонён с обоснованием, один признан несущественным.

**1. Растущий хвост в снапшотах — ИСПРАВЛЕНО.** Подтвердилось и оказалось хуже оценки: `history`
это Redis-ряд *на момент тика*, поэтому снапшот №2 несёт две точки, а №90 — девяносто. Стоимость
квадратична по длине матча: 45-минутная игра хранила ~4000 копий уже записанных точек. Поле
вырезается перед записью (`snapshotWriter`), и это единственное вырезанное поле. Проверено, что
его никто не читает обратно: `useMatchState` предпочитает поминутные строки архива и падает на
payload только когда их меньше — чего для записанного матча не бывает.

**2. Бандл >500 КБ — ИСПРАВЛЕНО.** `React.lazy` на все страницы кроме главной.
Вход: **794 КБ → 334 КБ** (gzip 210 → 104 КБ), предупреждение сборки ушло. MatchPage (416 КБ,
несёт таблицу предметов на 344 КБ) и TournamentPage (34 КБ) грузятся по требованию. HomePage
намеренно оставлена eager — ленивая загрузка первого, что видит посетитель, меняет один
round-trip на другой без выигрыша. Fallback намеренно пустой: спиннер на 200 мс читается как
рывок, а скелетоны страницы всё равно закрывают следующую за этим загрузку данных.

**3. Двойной `tallySeriesWins` в `/schedule/range` — ОТКЛОНЁН.** Свести в один запрос технически
можно (второй набор не зависит от первого), но выигрыш — один SQL-запрос на маршруте, который
уже делает два тяжёлых join, а цена — рефакторинг участка с тонкой логикой статусов серий
(`settle`, дедупликация нод и серий). Соотношение риска к пользе не в пользу правки. Записано
здесь, а не сделано молча.

**4. Общий ключ `['live-games']` у `useMatchDetail` и MatchPage — ОСТАВЛЕНО.** Посмотрел: это
осознанная конструкция (общий кэш, каждый наблюдатель со своим интервалом), TanStack это
поддерживает штатно, и оба интервала теперь корректно гаснут (C-3 в раунде 1). Хрупкость
теоретическая, симптома нет.

**5. Молчаливый отказ по тиру — ИСПРАВЛЕНО.** `archivePolicy` копит отказы по тирам и раз в тик
пишет один info-лог `{ byTier: { amateur: 12, unknown: 3 } }`; при нулевых отказах молчит. Раньше
причина была только на уровне debug, а прод работает на info — то есть рекордер мог тихо решить
не писать ничего, и ни одной строки об этом.

**Верификация:** server 30/387, client 33/329, оба tsc чисто, обе сборки (обычная и demo) проходят.
