# ЧТО ЭТО ЗА ПРОЕКТ

Real-time аналитика турнирных матчей Dota 2 + архив турнира. Монорепа, npm workspaces не используются —
три независимых `package.json` (`client/`, `server/`, `shared/` подключается по относительным путям).

**Frontend** — `client/`: React 19 + Vite 6 + TS + Tailwind 4 + TanStack Query v5 + React Router v7 + zustand.
**Backend (BFF)** — `server/`: Node 24 + Hono 4 + ioredis + zod 3 + pino + Drizzle ORM + postgres-js.
**Хранилища**: Redis (Upstash или локальный по `REDIS_URL`) — кэш апстримов; Postgres (embedded на **:55432**) — архив.
**Апстримы**: Valve Web API (ключ), `www.dota2.com/webapi` `GetLeagueData` (без ключа), OpenDota (без ключа), Stratz (токен, 500 req/hr).
**Деплой**: Vercel (клиент) + Railway (сервер), конфиги в репо, сервис выключен намеренно. Есть публичное демо —
статический реплей (`VITE_DEMO_MODE=1`, `client/src/demo/`, `demo-data/`).

Читай `CLAUDE.md` и `README.md` целиком — там описана архитектура и длинный список уже словленных граблей.
**Но**: документация — это гипотеза, а не факт. Всё, что там написано, проверяй по коду. Расхождение
«док говорит одно, код делает другое» — это самостоятельный дефект, фиксируй его.

## Путь данных, который надо пройти целиком

Каждый экран проверяется сквозным трейсом, слой за слоем:

```
внешний API → zod-схема (server/src/schemas/) → cached() + PQueue (server/src/cache.ts, queues.ts)
  → сервис (server/src/services/) → агрегатор (liveAggregator.ts) / ingest (services/ingest/ingestJob.ts, 30s)
  → Postgres (server/src/db/schema.ts) → маршрут (server/src/routes/{live,archive,heroes}.ts)
  → apiFetch (client/src/lib/apiFetch.ts) → useQuery (client/src/hooks/)
  → компонент (client/src/components/) → то, что реально видит глаз
```

Ключевые точки, которые уже исторически ломались (не считай их закрытыми — перепроверь):
`services/archive/seriesScore.ts` (три расходящихся источника счёта серии), `services/archive/reconstruct.ts`
(восстановление минуты без live-снимка), `schemas/leagueData.ts` (Valve меняет тип id посреди турнира),
`shared/buildingDecoder.ts` (`tower_state` лежит per-team внутри `scoreboard.*`), `services/teamLogo.ts`
(ugcid > MAX_SAFE_INTEGER), скрытые профили (`account_id === 4294967295`).

## Требования к доказательности

Для каждой находки обязательно:
- **точная ссылка** `путь/файл.ts:строка` (диапазон, если нужно);
- **сценарий воспроизведения** — конкретные входные данные/состояние → конкретный неверный результат.
  Не «может сломаться», а «при `game_state === 6` и пустом `series_infos` route вернёт X, а UI покажет Y»;
- **уверенность**: `ПОДТВЕРЖДЕНО` (прочитал код/увидел вывод) или `ГИПОТЕЗА` (нужна проверка в рантайме —
  и тогда напиши, какой именно эксперимент её закрывает);
- **радиус поражения** — какие ещё экраны/маршруты задеты той же причиной.

Запрещено: править код, рефакторить, придумывать несуществующие файлы/функции/поля API, выдавать
стилистические придирки за дефекты, дублировать одну причину в виде десяти находок (сворачивай в одну
с перечнем мест).

# ТРЕКИ АУДИТА

Пройди все. По каждому в отчёте должен быть раздел — включая явное «дефектов не найдено», если так.

### A. Корректность данных
Неверные вычисления и подмены смысла. Особое внимание: сторона vs команда (`radiant_win` — это про
сторону, не про команду), счёт серии, победитель, разница золота/опыта, K/D/A, тайминги, состояние
строений из битмаски, состояние/респавн Рошана, вероятность победы. Проверь единицы измерения и
часовые пояса везде, где есть время (`utils/day.ts`, календарь, расписание, `duration` vs `start_time`).

### B. Данные не приходят
Все причины пустого экрана. По каждому маршруту: что будет при 404/500/429/таймауте апстрима;
при **200 с пустым телом** (OpenDota так отвечает на неизвестный id); при `null` от Stratz;
при отсутствующей БД; при отсутствующем ключе. Где `Promise.allSettled` глотает отказ молча;
где `catch` возвращает `[]`/`null` и это неотличимо от «данных правда нет»; где отсутствующее поле
роняет весь парсинг zod вместо деградации; где ошибка одного блока обрушивает всю страницу.

### C. Данные не обновляются
Самый важный трек. Разбери **каждый** `useQuery` в `client/src/hooks/`:
- соотношение `staleTime` / `refetchInterval` (если `staleTime >= refetchInterval` — интервал молча
  пропускает циклы; см. комментарий PF-2 в `useDraftDetail.ts` — проверь, соблюдено ли это правило везде);
- `queryKey` — полнота (все ли параметры входят в ключ; нет ли двух разных наборов данных под одним
  ключом; `useMatchDetail` и `useLiveGames` намеренно делят `['live-games']` — не конфликтуют ли настройки);
- `enabled`, `gcTime`, `refetchOnWindowFocus`, `placeholderData`/`keepPreviousData` — где приводят к показу
  чужих или устаревших данных при переключении матча/турнира/минуты;
- останавливается ли опрос на `game_state === 6` (иначе жжётся квота);
- отсутствие инвалидации после того, как фоновой ingest записал новое.

Отдельно — серверный слой свежести: TTL в `server/src/cache.ts`, ключи `cached()` (нет ли per-user
компонент в ключе, нет ли коллизий), логика `stale:` копии, ретраи и `Retry-After` (`services/retryAfter.ts`),
очереди `queues.ts`. И цикл ingest (30s): что происходит при перекрытии тиков, при падении посреди тика,
при рестарте, при `INGEST_DISABLED`.

### D. База данных и запись
`server/src/db/schema.ts` + миграции в `server/drizzle/`: соответствует ли схема тому, что реально пишут
`snapshotWriter.ts`, `tournamentSync.ts`, `postMatchBackfill.ts`. Ищи: отсутствующие индексы под фактические
запросы, отсутствующие уникальные ограничения, батчи с дубликатами ключей в одном INSERT
(`ON CONFLICT DO UPDATE cannot affect row a second time`), гонки между ingest и чтением из маршрута,
частично записанные снимки, отсутствие транзакций там, где пишется несколько связанных таблиц,
неограниченный рост таблиц, дрейф между `bracket_nodes` / `series` / `matches`, расхождение
восстановленной минуты (`reconstruct.ts`) с записанной.

### E. Квоты и внешние API
Stratz 500 req/hr, ключ Valve, безлимитные на вид, но не бесконечные keyless-эндпоинты. Найди все места,
где число запросов растёт от числа зрителей, от числа матчей или от повторного рендера, а не от TTL.
Проверь `TRACKED_LEAGUE_IDS`: что происходит при пустом значении (по коду — «все живые лиги»), и не может ли
это снова поставить в очередь тысячи матчей.

### F. Типы и схемы
Все `as`, `any`, `!`, `@ts-ignore` — каждый как потенциальный дефект. Расхождения между `schemas/bff.ts`
и тем, что маршруты реально отдают; между этим и типами в клиентских хуках. `.passthrough()` там, где
он нужен, и его отсутствие там, где Valve/OpenDota добавляют поля. Толерантный парсинг id
(`leagueData.ts`) — нет ли где-то голого `z.number()`.

### G. UI-состояния
Для каждого экрана и каждого крупного блока: loading, empty, error, partial (часть панелей есть, часть нет),
reconstructed (`reconstructed: true` — сказано ли пользователю), stale (показываем старое — видно ли это),
скрытый профиль игрока, отсутствующий логотип команды, длинные имена, кириллица. Где скелетон висит вечно,
где `0` показывается как настоящее значение вместо «нет данных», где ошибка молчит.
Проверь границы ошибок (`BentoErrorBoundary`) — что именно они ловят и что происходит вне их зоны.

### H. Дизайн и вёрстка
Визуальная целостность: единообразие отступов, шрифтовых размеров, радиусов, цветов, состояний
(hover/focus/active/disabled), сеток bento-раскладки. Ищи расхождения между компонентами, решающими одну
задачу; захардкоженные значения там, где рядом используются токены; несогласованные тени и границы.
Отдельно: адаптивность на всех брейкпоинтах (узкий мобильный, планшет, широкий десктоп) — переполнения,
горизонтальный скролл страницы, обрезанный текст, схлопнувшиеся таблицы, нечитаемые графики.
Доступность: контраст, фокус с клавиатуры, `alt`, семантика, порядок табуляции, размеры зон нажатия.
Если можешь отрендерить — рендерь и смотри; если нет — говори, что вывод сделан по коду.

### I. Сборка, окружение, деплой
`.env.example` vs то, что реально читает `server/src/env.ts`. Что произойдёт при отсутствии каждой
переменной. Инлайн `import.meta.env` на этапе сборки (`apiBase.ts`, `apiFetch.ts`) — где это создаёт
расхождение dev/prod/demo. CORS. Пути сборки (`vercel.json`, `railway.json`, root directory и разрешение
`shared/`). Demo-режим: не может ли он протечь в обычную сборку и наоборот.

### J. Тесты
Не «есть ли тесты», а **лгут ли они**. Найди тесты, которые проходят при сломанной логике (замокан сам
предмет проверки, ассерты на `toBeDefined()`, тест дублирует реализацию). И перечисли непокрытые
критические места: то, что уже ломалось в проде, но не закреплено тестом.

### K. Системные причины (обязательный, главный раздел)
Отдельно от списка дефектов: **какие свойства архитектуры порождают этот поток багов**. Например —
одна и та же величина вычисляется в нескольких местах; нет единого источника правды по свежести данных;
внешняя ошибка неотличима от пустых данных; отсутствует контракт между BFF и клиентом, проверяемый
автоматически. Для каждой системной причины: какие из найденных дефектов она породила (по ID) и что
структурно её закрывает. Это раздел, ради которого делается весь аудит.

# ФОРМАТ ОТЧЁТА

Запиши результат в `AUDIT-REPORT.md` в корне репозитория. Ничего больше не создавай и не меняй.

Структура:

1. **Резюме** — 10–15 строк: общее состояние, где сосредоточена боль, сколько находок по уровням.
2. **Что фактически проверено** — вывод тестов, typecheck, сборки; поднимался ли стек; что проверить
   не удалось и почему. Честно.
3. **Сводная таблица** — все находки: `ID | Уровень | Трек | Файл:строка | Суть в одной строке | Уверенность`.
   Сортировка: сначала BLOCKER, внутри уровня — по радиусу поражения.
4. **Детали по каждой находке** — в порядке таблицы:

```
### [ID] Заголовок одной строкой
**Уровень:** BLOCKER | HIGH | MEDIUM | LOW
**Трек:** A–K
**Уверенность:** ПОДТВЕРЖДЕНО | ГИПОТЕЗА
**Где:** путь/файл.ts:120-134 (+ прочие места той же причины)
**Что происходит:** фактическое поведение
**Как воспроизвести:** конкретные входные данные/состояние → конкретный результат
**Почему это неверно:** ожидаемое поведение и на чём основано ожидание
**Что задето ещё:** экраны/маршруты/данные
**Направление починки:** 2–4 строки, без кода
**Оценка:** S (<1ч) | M (несколько часов) | L (день+)
```

5. **Системные причины** — трек K, с привязкой к ID.
6. **Порядок починки** — нумерованный список: что чинить первым и почему именно в этом порядке
   (зависимости, риск регрессии, эффект на симптомы владельца).
7. **Открытые вопросы** — где нужно решение владельца, а не техническая правка.

Шкала уровней:
- **BLOCKER** — показывает неверные данные как верные, теряет записанные данные, роняет экран, жжёт квоту.
- **HIGH** — данные не приходят или не обновляются в реальном сценарии; пользователь этого не понимает.
- **MEDIUM** — деградация в краевых случаях, кривое состояние UI, несогласованность дизайна.
- **LOW** — мелочи, чистота, задел на будущее.

Финальная проверка перед сдачей: пройди свой отчёт и вычеркни всё, что не подкреплено ссылкой на код
или наблюдаемым выводом. Лучше 40 доказанных находок, чем 150 с догадками.
